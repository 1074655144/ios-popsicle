# byron 显示链路定性验证：红蓝翻转测试

> 目的：用最少的假设，区分 fbverify 花屏的两种根因。这是封存后**成本最低**的一次验证。

## 为什么需要这个测试

之前的 `fbverify` 画了色条+棋盘格+文字，花屏时完全看不出图案，无法判断是：

- **断点 A（格式错）**：数据上了屏，但 SSPP 按 UBWC 压缩解读线性像素 → 花屏。
- **断点 B（没上屏）**：command-mode 面板 fastboot boot 后无持续刷新，写入的像素没被推到面板。

`fbflip` 用**整屏纯色**——它对 stride/width/字节序都不敏感。只要屏幕能在红蓝之间整体切换，
就证明 CPU→显存→面板链路是通的（问题只是格式）；如果纯色都不变色，说明链路本身不通。

## 镜像

`shim/fbflip/out/fbflip-boot.img`（6804 字节，纯 RAM，不写分区）
SHA-256 `51f8a3df4bfa3d0741b13fbe8ebbd8f295922c2a7068e5c0ca3d9cc0dbd86c57`

阶段（每阶段 6 秒，循环 3 轮 = 36 秒，然后自动重启回安卓）：
1. 全屏红
2. 全屏蓝
3. 上半红 / 下半蓝
4. 上半蓝 / 下半红

boot 后盯着屏幕看 36 秒，然后回答一个问题：**屏幕有没有在红 / 蓝之间整体变化？**

## 判定表

| 观察到的现象 | 结论 | 下一步 |
|---|---|---|
| 屏幕在红、蓝之间**整体翻转**（即使带点花） | 数据上了屏 → **断点 A：格式问题** | 攻克 UBWC：让 SSPP 接受线性源，或按 UBWC 格式写 |
| 屏幕**始终不变色**（静止花屏 / 旧画面） | 数据没上屏 → **断点 B：刷新或 buffer 地址问题** | command-mode 无持续刷新；需确认 ABL 交接后谁在推 DSI 帧 |
| 只有上下半屏分界在变、其余花 | 垂直 stride 有问题 | 用 SSPP 源 stride 寄存器实测值替换 4864 |

**注意**：纯色的"红/蓝"是按 ARGB word 语义写的；如果字节序反了，你看到的可能是"蓝/红"互换——
这不重要，重要的是**有没有颜色切换**。只要切换可见，链路就是通的。

## 真机结果（2026-11-21，用户目视确认）

**4 个阶段全部按预期显示**：
- 阶段 1/2：全屏红 ↔ 全屏蓝，整体切换明显。
- 阶段 3/4：上半红/下半蓝 ↔ 上半蓝/下半红，分界线平直居中，交替正确。

### 判定：断点 A 确认（格式问题），且 buffer 几何参数被间接验证正确

| 验证项 | 结论 |
|---|---|
| CPU → 显存 → 面板链路 | **通**：纯色写进去能上屏、能切换 |
| command-mode 持续刷新 | **正常**：fastboot boot 后 DSI 仍在推帧（断点 B 排除）|
| `fb_h=2608` / `fb_stride=4864` | **几何正确**：上下半屏分界平直且居中，说明垂直布局按预期 stride 推进 |
| 花屏根因 | **格式**：SSPP 按 UBWC 压缩解读 CPU 写的线性像素 |

### 为什么纯色能过、复杂图案花屏

这是 UBWC 的典型表现：UBWC 把图像切成 tile，对**纯色 tile 有 solid-color 快速路径**——
整屏同色时大量重复字节碰巧能被压缩解码器正确还原出色相；一旦是色条/棋盘格/文字，
每个 tile 内容不同，线性字节流被当 UBWC 解读就全面花屏。

因此 `fbverify` 的花屏不能推翻这次结论——它恰恰印证了"数据是线性写的、SSPP 按 UBWC 读"。

### 对参数的影响

- `fb_w=1216` / `fb_stride=4864` / `fb_h=2608`：**几何已被间接证实**，可视为定稿候选。
- `fb_format`：不是字节序问题（红蓝语义切换正常），而是**UBWC vs 线性**的编码格式问题。
- 剩余障碍从"4 个参数未定"收窄为"1 个架构问题：让 SSPP 按线性源显示"。

## 安全边界

- 全程 `fastboot boot`（RAM），不 flash、不写分区、不动 AVB。
- 36 秒后 PSCI 自动重启回安卓；长按电源键可提前重启。
- 不依赖 root（手机当前 KSU root 重启后已失效，本测试不需要）。
